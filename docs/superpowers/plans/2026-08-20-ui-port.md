# Doc-Intel UI Port Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port aroha-doc-intel's seven live dust screens (4,585 lines of React) into the runtime's vanilla template-literal UI as bounded modules, backed by the runtime's own endpoints where they exist and degrading honestly where they do not.

**Architecture:** Each screen becomes a TypeScript module under `src/ui/screens/` exporting a JavaScript string, composed by `page.ts` — the pattern `markdown.ts`/`styles.ts`/`templates.ts` already use. `page.ts` itself is not refactored. Every new module registers in `modules.test.ts`'s `JS_MODULES` so a parse failure names one file instead of blanking the interface. Screens whose backing API belongs to the paid add-on render a locked state driven by provider status rather than calling endpoints that do not exist.

**Tech Stack:** TypeScript (ESM, `"type": "module"`), Bun single-binary compile, vitest, headless Chrome via CDP. No bundler, no framework, no build step for the UI.

**Spec:** `docs/superpowers/specs/2026-08-20-unified-desktop-app-design.md` (§4 the interface port, §5 knowledge tiering)

**Source branch:** doc-intel screens live at `<doc-intel checkout>/frontend/src/screens/dust/` on branch `<doc-intel branch>`. **That branch is read-only for this plan — never commit, push, or modify anything in the aroha-doc-intel repo.**

## Global Constraints

- **No module exceeds 800 lines.** Where a source screen is larger, split it by responsibility during the port. (Spec §4.1)
- **Every module contributing JavaScript registers in `src/ui/modules.test.ts`'s `JS_MODULES` array** in the same commit that creates it. A module that contributes only CSS or data does not.
- **Write `\\n`, never `\n`, inside any string destined for the emitted script.** A single-escaped `\n` in source is consumed at build time and emitted as a real newline, terminating the string literal it sits in. This blanked the entire UI on 2026-08-19. Run `node --check` on the emitted script before committing.
- **The quote-parity assertion in `modules.test.ts` may be REFINED, never deleted.** It is the only automated check for the failure mode above. If a ported regex literal false-positives, extend `looksLikeRegexLiteral()`; do not loosen the count or skip the module.
- **Build DOM, never HTML strings.** The UI has a no-`innerHTML` invariant — stated in `markdown.ts:16`, `page.ts:632`, `page.ts:1679`, and unbroken: there is not one `innerHTML` assignment in `src/ui/`. Ported components return real elements via `document.createElement` and `textContent`, never a string that something later parses. *Amended after Task 1, which correctly refused the plan's original "functions returning HTML strings" wording.* Document text, model output, and peer-supplied names all flow through these components; parsing any of them as markup is the XSS the invariant exists to prevent.
- **Test the emitted string, not just the TypeScript twin.** Modules export testable TS functions alongside a duplicate inside the `String.raw` template. The duplicate is what ships. In Task 5 the two diverged — `escapeForRegExp` was double-escaped in the emitted copy, silently breaking mention-stripping for every hostname-shaped label — and every test passed, because they all exercised the twin. A parse check (`new Function(...)` not throwing) proves syntax, not behaviour. For any function duplicated across the two worlds, add a test that instantiates the emitted string, pulls the function out of scope, and runs the same assertions against it. *Added after Task 5.*
- **Absent add-on fields are absent, never faked.** `RetrievalHit.page`, `.artifacts`, `.score` are add-on-only. The built-in provider omits them; UI must render their absence, not a zero or a placeholder.
- **Do not modify `page.ts`'s existing screens.** `screens.test.ts` asserts their landmarks and is the regression net for this port.
- **Every task ends green:** `npm test` and `npx tsc --noEmit` from `apps/aroha-runtime`.

## What backs each screen

Surveyed before planning. The dust screens call doc-intel's **studio-backend** (`/api/v1/*`), which this runtime does not serve. Four screens map onto endpoints the runtime already has; three do not.

**Corrected 2026-08-20, after Task 2 read the sources.** The first version of this table was inferred from filenames and endpoint greps. Two entries were wrong and two were scoped too narrowly. What each screen *is* comes from its own header comment:

| Screen | Lines | What it actually is | Backing | Status |
|---|---|---|---|---|
| `PreviewPanel.tsx` | 276 | What an agent has drafted but not yet done, awaiting a human decision. Generic over any gated action. | The runtime's **existing** HITL flow — `page.ts:1102-1400`, `POST /v1/agents/:slug/v1/resume` | **Runtime-backed** |
| `Collection.tsx` | 773 | **One** screen for five workspace destinations: Agents, Knowledge, Tools, Skills, Spaces. Differences are declared as data. | `/v1/agents`, `/v1/knowledge`, `/v1/mcp`, agent skills routes | **Runtime-backed** |
| `Thread.tsx` | 500 | One conversation, any number of agents; each reply labelled with the agent that produced it. | `/v1/agents/:slug/threads` | **Runtime-backed** |
| `MentionComposer.tsx` | 414 | `@` opens a picker over agents, documents, tools **and** skills. Picking an agent decides who answers; anything else is granted to that one message. | `/v1/agents`, `/v1/peers`, `/v1/knowledge`, `/v1/mcp` | **Runtime-backed** |
| `DustApp.tsx` | 1,686 | Shell, routing, state. | routing over existing places | **Runtime-backed** |
| `DocumentReview.tsx` | 396 | Did this document go in cleanly, and can search find what it holds — including the self-healing questions list. | doc-intel's ingestion pipeline | **Add-on only** |
| `EmailSetup.tsx` | 269 | SMTP setup for someone who knows their address and nothing else; everything else derived from the domain. | no email connector exists in the runtime | **Deferred** |

**Ruling — add-on screens ship gated, not wired.** `DocumentReview` is ported structurally complete behind a single `addonAvailable` check derived from `status().kind === "addon"`, rendering a locked state naming what the add-on provides. It is NOT wired to `/api/v1/*` — that proxy is Plan 4's work, and inventing endpoints here would create a second API surface to delete later. *Cost if wrong:* one screen needs its fetch layer written in Plan 4 rather than merely unlocked.

**Ruling — `EmailSetup` is deferred out of this plan.** It configures an SMTP connector the runtime does not have. Porting it would produce a settings screen for a capability that does not exist — worse than absent, because it implies the feature ships. It returns when an email connector does. *Cost if wrong:* one 269-line screen ports later instead of now.

**Ruling — `PreviewPanel` restyles the existing approval UI rather than adding a screen.** The runtime already renders approvals and answers them via `/v1/resume`. Porting means adopting doc-intel's collapsible-tab presentation — a decided draft collapses itself instead of accumulating a wall of resolved cards — over the flow that already works. Building a second approval surface would split the HITL path in two. *Cost if wrong:* the restyle is reverted and `page.ts`'s approval block stands as it was.

**Excluded:** `WixDnsSetup.tsx` (156) — the DNS mechanism the user deferred. `ClaimSubdomain.tsx` (115) is **not** excluded; its addressing capability is integrated in Task 10 without the DNS steps.

**On code in this plan.** A port's specification is its source file. Tasks name the exact React file to read, the exact runtime endpoint to call, the exact module path to write, and the exact landmark test that must pass. They do not transcribe 4,585 lines of TSX into this document.
